3. NEW TWO-STAGE LOGIN AND STATE
=====================================================================

Browser -> nginx operator username/password (Basic Auth)
        -> FINOVA backend checks shared proxy token
        -> GET /api/auth/me checks email-login cookie
        -> POST /api/auth/send-code
              -> SMTP STARTTLS -> authorized Gmail sender
        -> POST /api/auth/verify-code
              -> SQLite checks hashed code, creates session
              -> HttpOnly Secure login cookie
        -> dashboard/financial API bound to login identity
        -> POST /api/auth/logout revokes session

Persistent on server: /opt/finova/data/auth.sqlite3
    (identities, challenge hashes, token hashes, send events)
    SQLite WAL sidecars require writable DIRECTORY.
    Old systemd ProtectSystem=strict needs ReadWritePaths exception.
    See README_CONFIGURATION.md Part H BEFORE deploying new source.

Financial uploads: server-memory sessions, cleared on logout/restart.
PDF extraction: private temporary data, cleaned after processing.

=====================================================================
4. MANUAL RELEASE PROCEDURE
=====================================================================

1. Finish features and tests locally; merge GitHub main.
2. SSH with personal private key to the Akamai Linode.
3. /root/finova-source: git pull --ff-only origin main.
4. Test source, review security and changed files.
5. Back up current /opt/finova and private SQLite state.
6. Stop finova; deploy reviewed tracked code to /opt/finova.
7. Ensure correct data ownership and systemd writable exception.
8. Start finova; verify backend, email login and user features.
9. Browser at SAME DuckDNS + HTTPS URL, hard refresh as needed.

Git push alone does NOT deploy the public site.
Domain, TLS, nginx and firewall normally remain in place on updates.

Security scope: restricted fictional-data hackathon demo; no real
financial records without a separate privacy/security/hosting review.
